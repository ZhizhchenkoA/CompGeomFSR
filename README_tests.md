# Автоматическое тестирование `geometry`: план рассказа и демонстрации

Этот документ — сценарий защиты проекта «Система автоматического тестирования geometry» на примере Geometry Workbench. Основное приложение позволяет работать с геометрией через Qt-интерфейс; здесь проверяются сами алгоритмы из `src/lib/geometry` без запуска окна. Для тестов выбран **Qt Test**, для общего запуска — **CTest**, для проверки изменений в репозитории — **GitHub Actions**.

## Что подготовить до выступления

- Открыть терминал **в корне репозитория** и редактор с файлами `tests/test_segments.cpp`, `tests/test_predicates.cpp`, `src/lib/geometry/predicates.cpp`.
- Убедиться, что доступны CMake, компилятор C++17 и Qt с компонентами Widgets и Test. На Debian/Ubuntu: `qtbase5-dev` для Qt 5 или `qt6-base-dev` для Qt 6.
- Для чистой демонстрации использовать отдельный каталог сборки `build-tests`. Существующая сборка приложения тогда не затрагивается.
- Если установлены обе версии Qt, указать `-DGEOMETRY_QT_VERSION=5` или `-DGEOMETRY_QT_VERSION=6`. Ниже показаны команды для Qt 6; при наличии только Qt 5 заменить `6` на `5`.

```bash
cmake -S . -B build-tests -DBUILD_TESTING=ON -DGEOMETRY_QT_VERSION=6
cmake --build build-tests --parallel 2
ctest --test-dir build-tests --output-on-failure
```

Ожидаемый итог последней команды: **5/5 наборов пройдены**, строка `100% tests passed, 0 tests failed out of 5`. Время выполнения зависит от компьютера.

## Как устроена система

```text
CMakeLists.txt
  └─ include(CTest), BUILD_TESTING
       └─ tests/CMakeLists.txt
            ├─ test_predicates  → geometry.predicates
            ├─ test_segments    → geometry.segments
            ├─ test_hull        → geometry.hull
            ├─ test_delaunay    → geometry.delaunay
            └─ test_polygon_boolean → geometry.polygon_boolean
```

Каждый `test_*` — самостоятельная программа Qt Test, связанная с библиотекой `geometry`. `add_test()` регистрирует её в CTest, а метки позволяют выбирать нужную область. `Q_OBJECT` и `private slots` делают методы класса тестовыми сценариями. Пара методов с суффиксами `_data` и без него задаёт таблицу входных данных и один общий код проверки. Общие операции сравнения точек находятся в `tests/test_helpers.h`.

Тесты используют данные, созданные внутри собственных методов. Им не нужны файлы, сеть, окно приложения или результат другого теста. Поэтому порядок запуска не влияет на ответ.

## Подробная демонстрация в терминале

### 1. Показать, что CTest видит все наборы

```bash
ctest --test-dir build-tests -N
```

В списке должны быть `geometry.predicates`, `geometry.segments`, `geometry.hull`, `geometry.delaunay`, `geometry.polygon_boolean`. Ключ `-N` только показывает список, не выполняя проверки. Затем запустить всё:

```bash
ctest --test-dir build-tests --output-on-failure
```

`--output-on-failure` оставляет обычный вывод коротким, а при ошибке показывает детали. Не нужно запускать пять исполняемых файлов вручную, чтобы получить общий результат.

### 2. Раскрыть отдельные сценарии Qt Test

```bash
./build-tests/tests/test_segments -v1
```

В выводе видны строки вида `intersectionCases(proper-crossing)`, `intersectionCases(endpoint-touch)`, `intersectionCases(collinear-overlap)` и другие. Имена заданы в `QTest::newRow(...)`; набор данных читается через `QFETCH(...)`. Для обсуждения открыть `tests/test_segments.cpp` и пройти по таблице:

| Случай | Входная геометрия | Ожидаемый ответ |
|---|---|---|
| `proper-crossing` | Два отрезка пересекаются внутри обоих | `Point`, координаты `(2, 2)` |
| `endpoint-touch` | Общий конец | `Point`, координаты `(2, 0)` |
| `parallel-separated` | Параллельные раздельные отрезки | `None` |
| `collinear-disjoint` | Одна прямая, но общего участка нет | `None` |
| `collinear-overlap` | Общий участок ненулевой длины | `Overlap`, концы `(2, 0)` и `(4, 0)` |
| `collinear-endpoint-touch` | На одной прямой есть только общая крайняя точка | `Point` |
| `contained-segment` | Один отрезок целиком внутри другого | `Overlap` |
| `vertical-overlap` | Общий вертикальный участок | `Overlap` |
| `identical-reversed` | Совпадающие отрезки с разным порядком концов | `Overlap` |
| `lines-cross-outside-segments` | Прямые пересекаются, но отрезки — нет | `None` |
| `point-on-segment` | Первый отрезок вырожден в точку | `Point` |
| `two-equal-points` / `two-distinct-points` | Оба отрезка вырождены | `Point` / `None` |

После этого показать `allSmallGridPairsAreSymmetric`: тест перебирает **6561** сочетание четырёх концов из сетки 3×3 и сравнивает пересечение `AB` с `CD` и `CD` с `AB`. В переборе автоматически встречаются и нулевые отрезки. Для наложения порядок двух концов общего участка не считается важным.
Дополнительно для каждого возвращённого пересечения проверяется, что его точка или оба конца общей части действительно лежат на обоих исходных отрезках.

### 3. Показать выбор одного набора и подробный вывод CTest

```bash
ctest --test-dir build-tests -R '^geometry[.]segments$' --output-on-failure
ctest --test-dir build-tests -L geometry -N
ctest --test-dir build-tests -R '^geometry[.]segments$' -V
```

`-R` выбирает по имени, `-L` — по метке, `-V` выводит детали запуска. У каждой цели задан таймаут 30 секунд, поэтому зависший тест не удержит CI бесконечно.

## Почему выбраны именно эти проверки

| Алгоритм | Обычный случай | Граница или вырождение | Проверка свойства |
|---|---|---|---|
| Предикаты | Левый и правый поворот | Коллинеарность, совпадающие концы, допуск, нулевой отрезок | При развороте `AB` знак поворота меняется |
| Пересечение отрезков | Пересечение внутри | Касание концом, параллельность, наложение, два отрезка-точки | Перестановка отрезков сохраняет результат; перебор сетки |
| Выпуклая оболочка | Квадрат с внутренними точками | Пустой ввод, одна или две точки, дубликаты, коллинеарность | Перестановка и перенос точек не меняют форму оболочки; её вершины идут против часовой стрелки |
| Триангуляция Делоне | Треугольник и несколько точек | Пустой/минимальный набор, дубликаты, коллинеарность | Ни одна другая точка не лежит строго внутри описанной окружности треугольника |
| Булевы операции | Перекрытие прямоугольников | Раздельность, вложение, совпадение, касание ребром или вершиной, пустой ввод | Формулы площадей для объединения, пересечения и разности; ориентация отверстия |

Для `turn(A,B,P)` знак определяется векторным произведением `(B−A) × (P−A)`: положительный — поворот влево, отрицательный — вправо, ноль — точки на одной прямой. Для отрезка точка может считаться лежащей на нём в пределах допуска расстояния, включая круг у конца отрезка. Для Делоне тест проверяет математическое свойство, а не жёсткий список треугольников: при точках на одной окружности возможны разные корректные разбиения.

### 4. Показать тест, который уже обнаружил ошибку

```bash
./build-tests/tests/test_polygon_boolean -v1
```

Показать `edgeTouchDoesNotCreateAreaIntersection`: прямоугольники имеют общую сторону, поэтому площадь пересечения равна нулю, объединение — один контур площадью 8, а разность первого и второго — исходный прямоугольник площадью 4. До исправления объединение возвращало пустой результат. В `src/lib/geometry/convex_polygon_boolean.cpp` теперь различаются общие рёбра с одинаковым направлением обхода (видимая внешняя граница) и с противоположным (внутреннее ребро объединения). Дополнительные сценарии проверяют частично общую сторону и общую диагональ.

Для вложенных прямоугольников тест `containedRectangleProducesHole` проверяет два контура разности: внешний идёт против часовой стрелки, отверстие — по часовой. Проверки площадей используют формулы `S(A ∪ B) + S(A ∩ B) = S(A) + S(B)` и `S(A \ B) + S(A ∩ B) = S(A)`, поэтому порядок начала контура не важен.

Затем показать `allSmallIntegerRectanglePairsHaveCorrectAreas`. Из четырёх координат сетки по каждой оси получаются 36 прямоугольников и **1296 упорядоченных пар**. Ожидаемая площадь пересечения вычисляется отдельно: ширина общего диапазона X умножается на высоту общего диапазона Y. По ней находятся площади объединения и разности. Это независимый эталон для трёх операций сразу; при сбое тест печатает координаты обеих фигур.

## Демонстрация обнаружения намеренной ошибки

Это самая убедительная часть защиты. Сначала сохранить **текущее** содержимое файла в каталоге сборки:

```bash
cp src/lib/geometry/predicates.cpp build-tests/predicates.cpp.before-demo
```

В редакторе открыть `src/lib/geometry/predicates.cpp`, найти функцию `turn` и **временно** заменить ровно одну строку:

```diff
- if (value > tolerance) {
+ if (value < tolerance) {
```

Теперь собрать только нужную тестовую цель и выполнить один набор:

```bash
cmake --build build-tests --target test_predicates --parallel 2
ctest --test-dir build-tests -R '^geometry[.]predicates$' --output-on-failure
```

Ожидаемый результат: команда `ctest` завершится **с ошибкой**; в выводе Qt Test будет `FAIL!` для `turnCases(left)` (и могут упасть другие случаи). Левый поворот стал распознаваться неправильно. Это ожидаемая красная проверка, а не поломка проекта.

Сразу вернуть сохранённую версию и повторить проверку:

```bash
cp build-tests/predicates.cpp.before-demo src/lib/geometry/predicates.cpp
cmake --build build-tests --target test_predicates --parallel 2
ctest --test-dir build-tests -R '^geometry[.]predicates$' --output-on-failure
git diff -- src/lib/geometry/predicates.cpp
```

Последняя команда должна показать тот же diff, что был **до** демонстрации; если файл до начала не менялся, вывод будет пустым. Сохранённая копия позволяет восстановить файл даже после прерванного показа. Намеренную ошибку нельзя оставлять в итоговой версии.

## Дополнительные фишки для показа

### Машиночитаемые отчёты

```bash
ctest --test-dir build-tests --output-junit test-results.xml
./build-tests/tests/test_predicates -o build-tests/predicates.xml,xml
```

Первый отчёт окажется в `build-tests/test-results.xml` и содержит сводку CTest в формате JUnit. Второй — `build-tests/predicates.xml` — содержит детализацию Qt Test. XML удобно загружать в CI и анализировать автоматически.

### Воспроизводимость и повторный запуск

```bash
ctest --test-dir build-tests --repeat until-fail:20 --output-on-failure
```

Команда повторяет тесты до 20 раз, останавливаясь на первом сбое. Она полезна для поиска нестабильных тестов. Сценарии здесь детерминированы: фиксированные точки и сетка, без случайного генератора.

### Проверка в GitHub Actions

Открыть `.github/workflows/test-geometry.yml`: workflow устанавливает Qt 5 и Qt 6 в двух заданиях, явно выбирает версию через `GEOMETRY_QT_VERSION`, собирает проект и вызывает CTest. При запуске на GitHub результаты JUnit сохраняются как артефакты `qt5-test-results` и `qt6-test-results`. `fail-fast: false` позволяет увидеть результат обеих версий, даже если одна не прошла.

## Короткие ответы на возможные вопросы

**Почему Qt Test?** Qt уже используется приложением. Тестовая зависимость добавлена только в отдельные цели, поэтому исходная библиотека `geometry` не становится зависимой от Qt.

**Почему пять программ, а не одна?** Можно быстро запустить нужную область; сбой в одном алгоритме не скрывает результат остальных. CTest всё равно запускает их одной командой.

**Зачем проверять свойства, если есть примеры с известным ответом?** Примеры проверяют конкретные координаты, а свойства охватывают целые классы преобразований и не требуют вручную выписывать каждый результат.

**Почему столько вырожденных случаев?** Именно на равенстве, касании, коллинеарности и пустом вводе чаще всего ошибаются условия ветвления и обработка размеров контейнеров.

**Что считать успешной защитой?** Показаны зелёный полный запуск, отдельные именованные случаи, красный тест после осмысленной ошибки и снова зелёный результат после восстановления.

## Итог

Проект показывает полный цикл автоматической проверки: алгоритм получает воспроизводимые входные данные, Qt Test сравнивает результат с ожидаемым поведением, CTest объединяет наборы, а GitHub Actions запускает их при изменениях. Демонстрация намеренной ошибки подтверждает, что тесты способны обнаруживать регрессию, а проверки свойств расширяют покрытие за пределы нескольких заранее выбранных примеров.
