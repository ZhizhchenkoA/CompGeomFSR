# Проект 2. CI: автоматическая сборка и тестирование Geometry Workbench

Этот документ объясняет, как работает непрерывная интеграция проекта и как показать её на защите. Конфигурация находится в [`.github/workflows/test-geometry.yml`](.github/workflows/test-geometry.yml). На **каждый push и pull request** GitHub Actions получает исходники, настраивает окружение, конфигурирует CMake, собирает C++/Qt-приложение и выполняет тесты. Сборка и тестирование не требуют запуска графического окна.

## Короткая схема

```text
push / pull request / ручной запуск
        │
        └─ 4 независимых задания: Qt 6 × GCC/Clang × Debug/Release
             │
             ├─ checkout: получить исходники
             ├─ install + cache: установить Qt, компилятор, CMake и ccache
             ├─ configure: сгенерировать сборку Ninja
             ├─ build: собрать библиотеки, приложение и тесты
             ├─ test: запустить пять наборов CTest
             ├─ diagnostics: сохранить логи и JUnit XML
             └─ artifact: упаковать и сохранить приложение для Qt 6 + GCC + Release
```

Все четыре сочетания обязательны для зелёного статуса. `fail-fast: false` позволяет остальным заданиям закончиться и показать свои результаты, если одно из них упало; оно **не** превращает ошибку в успех.

## Когда запускается workflow

- `push` — при отправке любого изменения в любую ветку репозитория, без фильтра по путям. Изменение C++-кода, CMake, тестов или документации запускает проверку.
- `pull_request` — при открытии или обновлении запроса на слияние. Это даёт результат до попадания изменений в основную ветку.
- `workflow_dispatch` — ручной запуск из вкладки **Actions** для повторной проверки или демонстрации.

Workflow использует `permissions: contents: read`: ему достаточно чтения исходников. Каждое задание выполняется на `ubuntu-24.04` с лимитом 30 минут.

## Матрица проверок

| Ось | Значения | Зачем |
|---|---|---|
| Компилятор | GCC (`g++`), Clang (`clang++`) | Найти различия в диагностике и компиляции |
| Режим сборки | Debug, Release | Проверить код без оптимизации и с оптимизацией |

Все задания используют **Qt 6** (`qt6-base-dev`). Матрица — декартово произведение `2 × 2 = 4` заданий. Каждое имеет своё имя вида `Qt 6 · GCC · Release`; в его параметрах явно указаны `CMAKE_CXX_COMPILER`, `CMAKE_BUILD_TYPE` и `GEOMETRY_QT_VERSION=6`. Поэтому установленный рядом Qt другой версии не может быть случайно выбран CMake.

## Этапы задания и поведение при ошибке

| Этап | Что делает | Что происходит при сбое |
|---|---|---|
| **Check out sources** | `actions/checkout` получает точную ревизию для текущего push или PR. | Следующие обычные этапы не запускаются. |
| **Install build dependencies** | Устанавливает CMake, Ninja, ccache, нужный Qt и компилятор из APT. | Задание красное; виден вывод установки. |
| **Restore compiler cache** | Восстанавливает кеш `ccache` для данного сочетания Qt, компилятора и режима. | Если кеша ещё нет, сборка просто выполняется с нуля. |
| **Configure** | Вызывает `cmake -S . -B build -G Ninja` с тестами и выбранной версией Qt. | Ошибка CMake делает этап и задание красными. |
| **Build** | Вызывает `cmake --build build --parallel 2`, собирая приложение и тесты. | Ошибка компиляции останавливает дальнейший тестовый этап. |
| **Test** | Запускает `ctest --test-dir build --parallel 2 --output-on-failure --output-junit test-results.xml`. | Падение хотя бы одного теста возвращает ненулевой код и делает задание красным. |
| **Upload diagnostic logs and test report** | Даже после ошибки сохраняет доступные логи и отчёты. | Помогает разобрать причину; отсутствующий отчёт после раннего сбоя допустим. |
| **Package Linux application** | После успешных тестов архивирует бинарник Qt 6 + GCC + Release в `tar.gz`, сохраняя право на запуск. | Ошибка упаковки делает задание красным. |
| **Upload Linux application** | Сохраняет архив с исполняемым файлом. | Если ожидаемый архив не создан, загрузка завершается ошибкой. |

Команды конфигурации, сборки и тестирования используют `set -o pipefail` и `tee`: вывод одновременно виден в журнале Actions и записывается в файл. `pipefail` сохраняет **ненулевой код CMake или CTest**, даже если `tee` успешно записал лог. Это важно для правильного красного статуса pipeline.

### Диагностика и артефакты

После каждого задания, включая неуспешное, шаг с `if: always()` загружает то, что успело появиться:

- `configure.log` — вывод настройки CMake;
- `build.log` и `ccache.log` — сборка и статистика кеша;
- `test.log`, `build/test-results.xml` и `build/Testing/Temporary/LastTest.log` — вывод CTest, JUnit XML и подробный журнал тестов.

Артефакт называется `diagnostics-qt6-<компилятор>-<режим>`; разные строки матрицы не перезаписывают друг друга. Для успешной сборки Qt 6 + GCC + Release появляется отдельный `GeometryWorkbench-linux-qt6-release` с внутренним архивом `tar.gz`. Архив сохраняет исполняемый бит бинарника после скачивания через GitHub. Для запуска нужны совместимые системные библиотеки Qt; это не универсальный установщик. Срок хранения артефактов в workflow — 14 дней.

### Кеш компиляции

`actions/cache` восстанавливает каталог `.ccache`. Ключ включает ОС, версию Qt, компилятор, тип сборки и SHA коммита; `restore-keys` позволяет взять кеш предыдущего коммита с теми же параметрами. `CMAKE_CXX_COMPILER_LAUNCHER=ccache` направляет компиляцию C++ через кеш. На первом запуске кеш пустой, на следующих изменениях могут повторно использоваться неизменившиеся объекты. Кеш влияет на скорость, **не** на критерий успешности тестов.

## Как запустить локально

Команды ниже воспроизводят одно задание матрицы: **Qt 6 + GCC + Release**. Выполнять их нужно из корня репозитория. На Ubuntu 24.04:

```bash
sudo apt-get update
sudo apt-get install --yes --no-install-recommends \
  cmake ninja-build ccache qt6-base-dev g++

cmake -S . -B build/ci-local -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_CXX_COMPILER_LAUNCHER=ccache \
  -DBUILD_TESTING=ON \
  -DGEOMETRY_QT_VERSION=6
cmake --build build/ci-local --parallel 2
ctest --test-dir build/ci-local --parallel 2 --output-on-failure \
  --output-junit test-results.xml
```

Каталог `build/` уже исключён из Git. Ожидается `100% tests passed, 0 tests failed out of 5`; отчёт появится в `build/ci-local/test-results.xml`. Для Clang замените пакет `g++` на `clang` и компилятор на `clang++`. Для Debug замените `Release` на `Debug`.

Если локально нет Ninja или ccache, можно убрать `-G Ninja` и `-DCMAKE_CXX_COMPILER_LAUNCHER=ccache`: логика CMake, сборки и CTest останется той же. В текущем репозитории обычная локальная сборка может выполняться через `build/`; отдельный `build/ci-local` удобен для воспроизведения CI без изменения её настроек.

### Что проверено в этой рабочей копии

- Локальная сборка **Qt 6 + GCC + Release** завершилась успешно; CTest показал `5/5` пройденных наборов.
- Временная замена ожидаемого результата `turnCases(left)` на неверный вызвала `FAIL!` и ненулевой код CTest; после восстановления файла все пять наборов снова прошли.
- YAML workflow прошёл проверку `actionlint`. Локально созданный `tar.gz` сохранил право запуска для бинарника.

Удалённые задания GitHub Actions и сборки Clang в этой рабочей копии ещё не запускались; их результат станет виден после отправки изменений в репозиторий.

## Как увидеть запуск на GitHub

1. Отправить рабочую версию в репозиторий: `git push`. Workflow запускается автоматически.
2. Открыть репозиторий → **Actions** → **CI — build and test** → последний запуск.
3. Проверить четыре строки матрицы. Открыть одну, например `Qt 6 · GCC · Release`, и раскрыть `Configure`, `Build`, `Test`.
4. Внизу страницы запуска открыть **Artifacts** и скачать `diagnostics-qt6-GCC-Release`. Посмотреть `test-results.xml` и `test.log`.
5. Скачать `GeometryWorkbench-linux-qt6-release` как результат успешной сборки. Из загруженного ZIP извлечь `GeometryWorkbench-linux-qt6-release.tar.gz`, затем выполнить `tar -xzf GeometryWorkbench-linux-qt6-release.tar.gz`. Значок статуса в корневом [`README.md`](README.md) ведёт на этот workflow.

До первого push с новым workflow на GitHub локальный файл существует, но удалённого зелёного запуска и артефактов ещё нет.

## Демонстрация красного и зелёного CI на защите

Работать лучше в отдельной ветке после публикации **исправной** версии проекта. Дождитесь завершения каждого запуска перед следующим push, чтобы на экране остались отдельные результаты.

### Вариант A: ошибка компиляции

1. Создать ветку `ci-demo` от исправной версии и отправить её. Показать зелёный запуск.
2. В [`src/lib/geometry/predicates.cpp`](src/lib/geometry/predicates.cpp), внутри `turn`, временно заменить `return 1;` на `return missing_symbol;`.
3. Зафиксировать только эту учебную ошибку и отправить ветку. В Actions этап **Configure** должен пройти, **Build** — упасть с сообщением о неизвестном имени `missing_symbol`; **Test** не запустится. `build.log` останется в диагностическом артефакте.
4. Вернуть исходную строку в редакторе, создать исправляющий коммит и отправить его. Новый запуск должен снова пройти все этапы.

### Вариант B: ошибка теста

1. В [`tests/test_predicates.cpp`](tests/test_predicates.cpp) временно изменить ожидаемый результат строки `QTest::newRow("left")`: вместо `1` указать `-1`.
2. Отправить учебный коммит в `ci-demo`. Этапы **Configure** и **Build** должны пройти, **Test** — упасть на `turnCases(left)`; детали будут в `test.log` и `LastTest.log`.
3. Вернуть ожидание `1`, отправить исправляющий коммит и показать следующий зелёный запуск.

Для короткой защиты достаточно одного варианта. Ошибку следует вернуть **новым исправляющим коммитом**, чтобы в истории Actions остались отдельные красный и зелёный запуски. Не переносите учебную ошибку в основную ветку.

## План рассказа на 10–12 минут

| Время | Действие | Что объяснить |
|---|---|---|
| 0:00–1:00 | Показать репозиторий и значок статуса в `README.md`. | CI автоматически проверяет каждое изменение. |
| 1:00–2:30 | Открыть workflow, показать `push`, `pull_request` и матрицу. | Четыре независимых сочетания покрывают два компилятора и два режима сборки с Qt 6. |
| 2:30–4:30 | Раскрыть шаги успешного запуска. | Получение исходников → окружение → CMake → сборка → тесты. |
| 4:30–6:00 | Показать `test.log`, JUnit XML и приложение в Artifacts. | Логи сохраняются для диагностики; приложение доступно для скачивания. |
| 6:00–8:30 | Открыть заранее подготовленный красный запуск. | Сбой компиляции проявляется в Build, сбой теста — в Test; `pipefail` не скрывает код ошибки. |
| 8:30–10:00 | Открыть следующий зелёный запуск. | После исправления та же автоматическая проверка проходит. |
| 10:00–12:00 | Показать команды локального запуска и ответить на вопросы. | Другой разработчик воспроизводит одну строку матрицы у себя. |

Если на защите нет времени ждать GitHub, подготовьте три уже завершённых запуска: **зелёный → красный → зелёный**, а правку покажите по двум коммитам.

## Частые вопросы

**Почему матрица не скрывает ошибки?** `fail-fast: false` лишь отменяет автоматическую остановку остальных заданий. Одно красное обязательное задание делает красным весь workflow.

**Что произойдёт, если тест упадёт?** `ctest` вернёт ненулевой код. Благодаря `pipefail` он сохранится после `tee`; шаг Test и задание будут неуспешными. Логи всё равно загрузятся через `if: always()`.

**Зачем Debug и Release?** Разные флаги оптимизации и отладочные настройки помогают обнаружить ошибки, которые проявляются только в одном режиме.

**Зачем кеш, если сборка и так быстрая?** На учебном проекте он показывает типичную практику CI; при росте проекта повторные компиляции становятся заметно дороже. Кеш не заменяет тесты.

**Почему не публикуется готовый установщик?** Задание требует сохранить собранное приложение как артефакт. Workflow сохраняет Linux-бинарник в `tar.gz`; упаковка Qt-библиотек в переносимый дистрибутив — отдельная задача.

## Итог

CI превращает локальные команды CMake и CTest в повторяемую проверку каждого изменения. Красный запуск указывает на этап и хранит диагностику, зелёный подтверждает успешную сборку и тестирование всех четырёх сочетаний. Отдельный артефакт позволяет скачать собранное приложение, а значок в README показывает состояние workflow.
